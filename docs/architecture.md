# Архитектура и решения

## Заказ

1. Клиент отправляет ID блюд, количества и контакт.
2. Pydantic проверяет размеры и обязательность полей.
3. `OrderService` выбирает блюда из текущего меню. Цены и названия клиента игнорируются.
4. `Decimal` рассчитывает сумму без ошибок двоичной арифметики.
5. `OrderRepository` фиксирует неизменяемый снимок состава, цен и контактов.
6. Только после commit отправляются уведомления. Отказ одного получателя не блокирует остальных.
7. Ответ содержит ID сохранённого заказа и отдельный статус доставки уведомления.
8. Callback администратора меняет `pending → accepted` условным SQL UPDATE: только один победитель.

В PostgreSQL добавляется таблица `orders`; прежняя `users` не удаляется и не переписывается.
Хранение суммы строкой в JSON сохраняет точность и историческую цену.

## Меню и источник истины

`instruction.json` — стартовые данные. `data/menu.json` — рабочая копия. У всех записей есть
ID: для старых записей он генерируется детерминированно, затем сохраняется. После этого
переименование и перестановка не меняют ID. Записи с категорией `info` не попадают в каталог.

Запись через временный файл + `os.replace` предотвращает частично записанный JSON.
Поэтому монтируется каталог `data`, а не один файл: `os.replace` поверх file bind mount
не работает. Архитектура рассчитана на один пишущий экземпляр; для нескольких нужен
общий транзакционный каталог в БД, а не JSON на локальных дисках.

В исходном двуязычном `text` встречаются цены/контакты. При ответе о цене authoritative
поле — `metadata.price`. После редактирования состава администратор должен обновлять и
описание: система не умеет самостоятельно восстановить ингредиенты.

## Retrieval

- Сначала распознаются явно названные категории: breakfast, crepe, pasta, vegetarian,
  vegan и FAQ. Категорийный запрос выбирает все соответствующие записи, не top-k.
- Vegetarian не означает vegan. Без явного признака нельзя обещать отсутствие аллергенов.
- У коротких уточнений используется предыдущая реплика гостя.
- Семантический путь: RoSBERTa → Qdrant cosine similarity → ограниченный контекст.
- Отпечаток SHA-256 считается по содержимому, а не числу строк. Все векторные точки содержат
  версию меню. Обновляются изменённые данные и удаляются устаревшие точки; обычное изменение
  меню не удаляет коллекцию. Изменение размерности требует отдельной миграции.
- Для новой версии используется отдельная коллекция `pastabar_menu_v2`: старый индекс не трогаем.
- Ошибка модели/Qdrant переводит сервис в lexical fallback. Категории работают без модели.
- Векторы и запросы выполняются в worker thread с сериализацией доступа к модели.
- Модель не вызывается при импортировании. HTTP readiness не зависит от скачивания весов.

Не найденный результат не доказывает отсутствие блюда во всём меню. Инструкция LLM требует
честно сообщить о недостатке контекста и предложить менеджера, а не выдумывать отказ.
Контекст ограничен 18 000 символами с явной отметкой усечения.

## Границы слоёв

- `routes/*`: протокол HTTP, авторизация, перевод ошибок в коды ответа.
- `orders`, `assistant`: сценарии приложения.
- `menu`, `database`, `history`, `media`: хранение данных.
- `retrieval`, `telegram`: внешние интеграции.
- `runtime`: единственная точка сборки зависимостей.

Отдельный DI-фреймворк и микросервисы не нужны для такого масштаба. Explicit constructors
позволяют тестировать бизнес-логику без сетей, а приложение — с временной SQLite.

## Безопасность и ограничения

Админский доступ закрыт без настроенного длинного токена. Сравнение constant-time.
Токен хранится браузером админки: используйте HTTPS и доверенное устройство. Для команды
лучше индивидуальные учётные записи и audit log. Telegram ID гостя берётся только из
проверенной HMAC-подписи с `auth_date`, а не из тела запроса.

Файлы изображений проверяются Pillow, расширение определяется содержимым. Видео имеет
лимит 100 MB, но не транскодируется и не проходит антивирус. Не публикуйте upload API без
HTTPS, секретного токена и ограничений тела на reverse proxy. Неавторизованная отправка
заказов допустима как гостевой сценарий; от массового спама нужны edge-защита/CAPTCHA.

История Redis ограничена 20 сообщениями с TTL сутки. Заказы содержат персональные данные:
нужны политика хранения, ограниченный доступ и защищённые backup. Не логируйте `.env` и токены.
